Settings should answer one question first: can every project run?

Today it answers a different one: what is configured. The parts underneath are sound. The page shows them as eight separate forms, in 2,344 words, with green badges for keys nobody has seen work.

Status: built. All three phases are in the app. The sample keys are fake, so the built page shows what it should: Anthropic answered its key with a real 401 and reads Failing, the keys nothing has called read Untested, and nothing is green. At 1440px on the same seed: words on screen 2,344 → 1,405, the Providers page 2,475px → 1,096px (1,972px on a phone, from 4,808), its buttons 65 → 23, and browser confirm() dialogs 6 → 0.

AThe verdict

The pieces are well made: a readiness report that names every refusal with a one-press fix, a connect flow that tests the key before you leave, a paid check that shows its cost before it spends, and an import that previews every row before writing. The page around them is the problem.

Each section was built as its own form with its own way of saving, warning and confirming. Every provider gets the same full-size card whether it is healthy or blocked. Rail notes describe sections instead of reporting their state. The strongest signal on the page, a green Ready, means "yaaf would not refuse this seat". It does not mean the key works: three sample keys that could never answer all showed green.

The fix is not fewer settings. It is one landing that answers "can everything run, and what needs me", health folded into the rows it describes, and a single small kit every section is built from.

The three changes that move it most

1An Overview that lands first

“Needs you” ranked by consequence, a matrix of what each class runs on per provider, and one tile per connection. It reads the same readiness report that refuses seats, so it can never disagree with them.

2Green means it answered

Split “will yaaf allow it” (the badge) from “have we seen it work” (a seal: answered 14 min ago, never, refused the key). The data exists: runs record provider, status and error kind.

3One kit, eight sections

One section header, one status vocabulary, one secret-field pattern, one action hierarchy with costs on the button, one save model, in-page confirmations that show consequences before the press.

Limits of this assessment

The live instance (yaaf-app.dplouffe.ca) was blocked by this environment’s network policy, so nothing here was observed on it, and the test account was not used. Every screenshot comes from the same code (42d1545) run locally with sample data shaped like a real install. Verified below means observed in that local build. Code means read in the source but not exercised. Hypothesis means plausible, not checked. Proposal marks a design that does not exist. No real users were tested. Time-on-task figures would be estimates, so none are given. Every number in this report is measured or counted.

North star

An admin opens Settings and, before reading a sentence, sees one of two things: “Everything can run” with the evidence beside it, or a short list of what can’t, each with the button that fixes it. Every section below it reads the same way: what it is, its state, how we know, and the one thing to do next. Detail is one click away, never in the way, and nothing powerful has moved more than one click further than it is today.

+Method

The live site was unreachable from the research environment (network policy), so the product was run locally at 42d1545: tests/e2e/demo.py seeded 8 projects. seed/configure.py then added, through the same admin API the page calls, five keys across four providers (one hidden), a Founder key, Slack and web search settings, three invited people and two tokens. Every key is fake, so no call could succeed. That is what exposed the Ready badge. seed/capture.js took every section at 1440px, 390px and in dark mode, and counted words, controls and folds. The page, its eight section components and the shared readiness, provider and copy modules were read in the source.

The mockups (mockups.html) use only the product’s tokens and render with seed/render.js. No product code was changed.

Skipped deliberately: a separate visual identity (the product has a good one) and a navigation redesign beyond Settings. The sidebar’s “Workspace” group is out of scope.
